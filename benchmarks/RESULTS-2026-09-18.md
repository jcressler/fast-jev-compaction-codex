# Initial live Jev experiment — 2026-09-18

Version tested: 0.3.0. Jev returned model `jev-1.13.0`.

This is an integration and evidence-selection experiment, not a measurement of
coding accuracy, repeated actions by Codex, or overall task cost.

## Evidence coverage at a 6,000-character recovery budget

| Synthetic case | Original local index | Same candidate pool, equal scores, no API | Live Jev ranking |
| --- | --- | --- | --- |
| Prior successful write and failed patch | 100% | 100% | 100% |
| Later instruction correction | 100% | 100% | 100% |
| Earlier successful lookup needed for continuation | 0% | 100% | 100% |

All three modes retained the checked constraints in every case. The targets
were scored by evidence ID locally and were not included in selection queries.
Every case used one independent synthetic capture with 79 indexed entries.
Jev considered 20 candidates per case. These small fixtures do not establish
long-running or repeated-compaction performance.

The shared-pool control explains the observed coverage improvement: the
shortlist alone included the older lookup. **This experiment does not show
that Jev's ranking improves over the stronger local control.** It shows that
the new Jev path works and preserves the selected evidence in these fixtures.
The equal-score control is only one local ordering, not every possible local
retrieval strategy. The control was added after the first live run to check
this confound; it reused the unchanged fixtures and made no further API calls.

## Live measurements

| Case | Selector wall time | Reported input tokens | Reported output tokens |
| --- | ---: | ---: | ---: |
| Prior write/failure | 529 ms | 6,306 | 375 |
| Instruction correction | 271 ms | 6,314 | 375 |
| Earlier lookup | 235 ms | 6,335 | 375 |

The local candidate-pool control took approximately 44–46 ms per case on this
machine. Timings include local selection work and, for Jev, the API request.
They are single samples, not latency distributions. No dollar cost is inferred
from token usage and no cost-saving claim is made.

## Integration checks

- A synthetic connectivity request succeeded.
- The installed plugin's CLI handled `PreCompact` with a real Jev call, then
  `SessionStart` with source `compact` restored a bounded selected index once.
  It included the older lookup and left the source transcript unchanged.
  That call took 789 ms and reported 7,457 input / 451 output tokens. This test
  invoked hook events directly, rather than relying on Codex to dispatch them.
- A separate native compaction and continuation test passed on Codex CLI
  0.155.0 using `gpt-5.6-luna`, with the plugin disabled. It retained a synthetic
  receipt ID, quantity, upload constraint, and the instruction not to repeat
  a write. This is a native compatibility check, not an integrated plugin test.
- Bundled CLI 0.142.3 was rejected by the service for requiring a newer CLI.
  The newer CLI was installed only in the temporary test directory.
- Typecheck, build, 82 unit/integration tests, and offline benchmark self-tests
  passed. Only synthetic data was sent to Jev. No key was committed.

Five Jev requests were made in total: one connection check, three selection
comparisons, and one installed-hook check. Reported combined usage was 26,719
input tokens and 1,596 output tokens. No private Codex session was submitted.

## What remains unproven

An end-to-end comparison with Codex automatically dispatching trusted plugin
hooks, repeated native compactions, and a held-out suite of tasks remains to
be run. Keep native-only, local-recovery, shared-pool-local, and Jev arms on the
same model and fixtures. Measure task accuracy, repeated failed attempts or
side effects, full latency, and actual billed cost. The current evidence is
insufficient to recommend Jev ranking over local candidate selection.
