# Longer native Codex + Jev evaluation — September 18, 2026

Jev-assisted recovery matched native Codex on this task. Both scored 100/100;
the two offline recovery variants scored 84/100. This establishes a working
native-compaction integration with real Jev calls, but does not establish an
accuracy or cost advantage over native Codex.

| Mode | Score | Final receipt audit | Elapsed | Native compactions | Jev calls |
| --- | ---: | --- | ---: | ---: | ---: |
| Native Codex | 100/100 | Correct | 225.6 s | 3 | 0 |
| Local heuristic recovery | 84/100 | Wrong receipt ID and quantity | 302.1 s | 3 | 0 |
| Candidate-order control | 84/100 | Wrong receipt ID and quantity | 379.2 s | 3 | 0 |
| Jev-assisted recovery | 100/100 | Correct | 243.4 s | 3 | 3 |

All four implementations passed the hidden code-behavior checks. All retained
the corrected fulfillment/quantity rules, kept uploads disabled, made no receipt
apply attempts, and did not retry the failed legacy preview. The entire 16-point
deduction in the offline variants came from the factual `audit.json` check.

The expected audit contained receipt ID `receipt-RR-0918-042-r2` and received
quantity `25`. Local recovery instead wrote order ID `RR-0918-042` and quantity
`18`; the candidate-order control wrote that order ID and quantity `0`.

## What ran

Pinned Codex CLI **0.155.0**, model **gpt-5.6-luna**, medium reasoning effort,
one run per arm in the order shown. Each run used a fresh task workspace, the
same four user prompts, the same initial files, and simulated receipt tools.
Four approximately 16 KB diagnostic files supplied ordinary tool-output noise.

The task implemented a pure inventory-reconciliation function, inspected an
already-committed receipt and an unsupported legacy preview, then corrected an
earlier fulfillment/case-pack requirement. Later stages added validation and
required a final audit based on earlier evidence. Golden checks were withheld
until final submission. Native compaction ran between stages: **12 completed
compactions across all four runs**.

The fixture and protocol were saved before each live run; both batches have the
same fixture hash in [the aggregate JSON](LONG-TASK-2026-09-18.json). No task
prompts, expected outputs, or scoring weights were tuned after seeing results.
The published evaluator improves one failure-description string without
changing the scoring predicate.

For the recovery variants, Codex itself dispatched reviewed/trusted user hooks
in an isolated profile. Those hooks called the production capture/selection/
restoration code through a telemetry wrapper. Every recovery arm recorded
**three captures and three nonempty post-compaction restorations**. The test did
not manually call hooks or inject a fabricated recovery transcript.

The candidate-order control uses the same candidate-generation algorithm as
Jev, with equal scores from an in-process scorer and zero network requests.
These are independent coding runs: their transcripts and actual candidate
records differ. This control is not a paired replay of identical evidence.

## Jev and usage measurements

All three live selections returned **`jev-1.13.0`**, with no local fallback.
They consumed **23,069 input tokens and 672 output tokens** in total. Measured
whole PreCompact hook times were **1,191 ms, 533 ms, and 595 ms**, totaling
**2.319 seconds** including capture and selection.

| Mode | Reported native input | Cached input | Input minus cached | Native output |
| --- | ---: | ---: | ---: | ---: |
| Native Codex | 723,808 | 599,296 | 124,512 | 9,426 |
| Local heuristic recovery | 512,579 | 356,864 | 155,715 | 7,410 |
| Candidate-order control | 744,354 | 615,680 | 128,674 | 8,076 |
| Jev-assisted recovery | 334,840 | 227,584 | 107,256 | 5,434 |

These are cumulative app-server counters. Separate native-compaction billing
was not observed. Jev usage is additional and belongs to a different provider.
No dollar costs were inferred. Fewer reported native tokens in one stochastic
run do not prove savings; the Jev run was about 18 seconds slower than native.

## Retrieval weakness exposed

Local recovery made six archive searches. The candidate-order control made
nine searches and one retrieval. Both still wrote an incorrect audit. The Jev
run made no archive search or retrieval calls, so its correct audit does not
prove that it successfully recovered the buried receipt from disk.

The local archive preserved the authoritative receipt, but Codex had batched
several calls into one outer `exec` result. A 16,280-character diagnostic result
preceded the 554-character receipt and 190-character legacy result. The short
searchable summary/outcome did not expose the receipt facts. Searches for the
inner tool name, receipt field name, legacy term, and order ID returned no
matching entry. A broad diagnostic phrase produced a misleading match.

The next priority is search coverage inside batched results: preserve result
chunk boundaries and bounded excerpts from each chunk, or provide a bounded
raw-record search fallback. Jev ranking should be tested again after that,
using paired candidate snapshots and repeated held-out tasks. No search/ranking
change was applied during this experiment.

## Compatibility fixes shipped with the results

- **0.3.1 package discovery:** removed the root portable `plugin.json`, allowing
  the supported `.codex-plugin/plugin.json` and default `hooks/hooks.json` path
  to load. A fresh isolated 0.155.0 installation reports both hooks with
  `source: "plugin"`. The pinned runtime's [manifest loader](https://github.com/openai/codex/blob/f0a1b8f0849d90960bc406b848f32e5a129b0457/codex-rs/core-plugins/src/loader.rs)
  skips hook loading for the portable Agent Plugin format. The native task
  comparison used the user-hook bridge; bundled-plugin discovery was checked
  separately and still requires normal trust review after installation.
- **Legacy archive-compactor compatibility:** accept textual arrays in persisted
  `custom_tool_call_output` records and keep call/result pairs atomic. Malformed
  or non-text arrays remain opaque. This fixes the separate legacy compactor;
  the recovery archive path used by this experiment already supported these
  records and was not changed.

Local validation passed: **83 tests**, type checking, build, all offline
benchmark self-tests, plugin validation, and skill validation. The live run used
only synthetic task data. Temporary test credentials were removed, and the
repository passed an exact-key scan before publication.

## Limits on the conclusion

This is one task and one sample per arm, in fixed order. The baseline used the
existing authenticated profile; the recovery arms used an isolated profile.
The model, effort, base instructions, supplied tools, and task prompts were
explicitly configured, but this is not a fully isolated causal experiment.
Compactions were manually triggered at stage boundaries, not by exhausting the
context window. Tool counts cover supplied dynamic tools rather than every
built-in Codex wrapper or failed patch attempt. Repeated file reads can be useful
and are not automatically mistakes.

The result supports continuing the experiment. It does **not** support recommending
Jev recovery over native Codex defaults yet.
